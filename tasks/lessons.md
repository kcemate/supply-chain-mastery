# Lessons

- When a user relaxes a provider-specific requirement, optimize for the product requirement instead. For audio, “voices that don’t sound robotic” matters more than preserving an xAI-only pipeline.
- When the user provides a visual reference and says fidelity is the source of truth, a checklist of included UI blocks is not enough. The first screenshot must match the reference composition and material realism at a glance; if it reads as a stylized web mockup, keep iterating before calling it done.
- For reference-image UI work, first lock geometry to the image proportions before adding texture. A visually rich but flow-based layout will still fail if the header, clipping, CTA, audio, and ledger are not in the same bands as the reference.
- Before account/backend work, honor the latest product baseline even if the current runtime files contain an experiment. Restore the known-good UI first, then layer persistence behind the existing state shape.
- For hosted progress sync, keep one frontend persistence boundary. Existing curriculum/audio interactions can keep calling `saveState()` as long as that function delegates to a real `stateStore` adapter with local cache, remote sync, and retry behavior.
- For Excel upload products, do not rely only on synthetic ExcelJS-generated fixtures. Real `.xlsx` files can use valid OOXML namespace prefixes and relationship/table metadata that ExcelJS cannot parse; keep a tolerant reader fallback and a regression test against the user-provided workbook shape.
- Browser-specific error wording matters. Safari can report parser crashes as `undefined is not an object (evaluating 'M.sheets')`, so compatibility fallback checks need regression coverage for Safari-style messages, not only Chrome/Node messages.
- For anonymous here.now publishes, do not hide the claim URL behind a Markdown label. Show the raw URL plus slug/token separately so query parameters are visible and recoverable if a client rewrites links.
- When the user sets an “Apple/keynote-stage” quality bar for a visual 3D product, a functional first pass is not enough. Do not mark the goal complete just because features exist and tests pass; keep iterating on composition, fidelity, spacing, hierarchy, and visual delight until the screenshot itself feels demo-worthy.
- When the user changes direction from rebuilding a diagram to editing an exact supplied image, preserve the exact image as the visual source of truth. Build precise editable overlays and export around that image instead of forcing the previous structured/3D approach.
- When the user explicitly reframes a PNG as only a specification, do not keep the PNG as the rendered artifact. Rebuild the scene as structured data with live vector/DOM text, even if a previous task favored exact-image overlays.
- When the user challenges whether a visual build is truly final, inspect the actual in-app browser viewport they are using before answering. Desktop smoke shots can miss toolbar wrapping, wasted stage space, and projection-readiness issues.
- When the user asks to keep improving and "use all the power," escalate beyond small spacing fixes. Add product-quality behaviors like immersive stage mode, motion/state polish, clearer visual relationships, and export-safe presentation details.
- Before telling the user to reload a local app, verify the exact URL and port they have open is still being served by this workspace. A different Vite app can occupy the default port while the shared browser URL points at a stopped fallback port.
- Browser smoke tests for local apps must not assume a fixed port is ours. Pick an available port and start this workspace directly, or the test can silently inspect a different local preview and produce misleading failures.
